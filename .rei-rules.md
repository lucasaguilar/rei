# REI MASTER RULES - Angular & TypeScript Expert

Refactoring Standards: Always perform atomic refactors. If a symbol's name or signature changes, you must update all call sites across the project in the same turn to maintain type safety.

## 1. General TypeScript Standards
- **Strict Typing**: PROHIBIDO el uso de `any`. Usa tipos específicos o `unknown`.
- **Null Safety**: Usa encadenamiento opcional `?.` y operador nullish coalescing `??`.
- **Async Patterns**: Usa siempre `async/await` para operaciones secuenciales.
- **Naming**: 
  - Interfaces: PascalCase (ej: `UserEntry`).
  - Métodos/Variables: camelCase.
  - Tipos: Sufijos descriptivos (`*State`, `*Data`, `*Type`).

## 2. Angular Modern Standards (Signals & Functional)
- **Dependency Injection**: Usa únicamente la función `inject()` con `readonly`. (PROHIBIDO el uso de constructores).
- **Reactivity**: Usa `signal()`, `computed()` y `selectSignal()`. (PROHIBIDO propiedades tradicionales para datos reactivos).
- **Component API**: Usa `input()`, `input.required<T>()` y `output<T>()`. (PROHIBIDO @Input y @Output).
- **Template Syntax**: Usa exclusivamente el nuevo flujo de control (`@if`, `@for`, `@switch`).
- **SignalStore**: 
  - `withDevtools` siempre como primer parámetro.
  - Lógica de negocio siempre en `withMethods`.
- **Components**: Siempre `standalone: true` y `ChangeDetectionStrategy.OnPush`.

## 3. REI Internal Architecture Rules
- **Atomic Patches**: Si cambias una interfaz o firma de método, DEBES buscar y actualizar todos los archivos que lo consumen en el mismo turno.
- **Logging**: Usa siempre el `AgentLogger` con el `correlationId` correspondiente.
- **Search & Replace**: Asegúrate de que los bloques `<search>` coincidan exactamente con la indentación del archivo original.
- **No Documentation**: NO crees archivos `.md` de documentación a menos que el usuario lo pida explícitamente.

## 5. Anti-Hallucination & Patch Precision
- **Zero-Assumption Edits**: PROHIBIDO proponer un `<edit>` sobre una sección de código que haya sido marcada como truncada en el contexto. Si el código está truncado, DEBES usar `<request_files>` primero.
- **Whitespace Rigor**: Antes de emitir un bloque `<search>`, verifica que los espacios, tabs y saltos de línea sean idénticos al original. No intentes "limpiar" la indentación en el bloque de búsqueda.
- **Cross-File Impact Analysis**: Cada vez que modifiques una firma de método, clase o interfaz, DEBES ejecutar mentalmente (o vía herramientas) un escaneo de callers para asegurar que ningún archivo quede en estado inconsistente.
- **Atomic Refactor Enforcement**: Si un cambio de nombre afecta a un símbolo exportado, el turno NO se considera finalizado hasta que todos los archivos referenciados en el Skeleton Map hayan sido actualizados en el mismo set de parches.
- **Granular S&R**: Divide los cambios grandes en múltiples bloques `<edit>` pequeños y específicos. Evita bloques de `<search>` excesivamente largos para minimizar errores de coincidencia por whitespace.
- **Import Integrity**: Cada vez que introduzcas una nueva dependencia, clase o función externa en un archivo, DEBES incluir un bloque `<edit>` adicional para actualizar la sección de imports al inicio del archivo.
- **Project Context Alignment**: Antes de proponer código, verifica el `package.json` y `tsconfig.json` para asegurar que la sintaxis (ESM vs CJS) y las capacidades del lenguaje sean compatibles con la configuración del proyecto.

## 4. Accessibility (A11y)
- **Headings**: Al refactorizar encabezados, garantiza que la apariencia visual no cambie (revisa selectores CSS).
